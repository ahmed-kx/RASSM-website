# RASSM

E-commerce website for **RASSM**, an Algerian streetwear brand. Tagline: **"Draw what you can't say."**
Oversized hoodies, sweatshirts and t-shirts with artistic sketch prints.

- Prices in Algerian Dinar, integers only, always displayed as `7 900 DA` (narrow no-break space for thousands, `DA` after the number, discounts as `−100 DA`) (use `formatPrice` from `@rassm/shared`, never format by hand).
- Cash on delivery only, to the **58 wilayas** of Algeria (home delivery or stop desk), shipped by our courier **Anderson** from Alger. Some wilayas have **no stop desk** (see Business rules).
- **Sales flow (Meta Ads):** visitors land on a product page from an ad and order that product directly with the form on the page. There is **no cart and no checkout page**: one order = one product (one color, one size, a quantity). After the order, the customer lands on `/merci` ("commande reçue") and the team calls them: **the order is confirmed only after this phone call**.
- Customer-facing language is **French** (see Language rule below).
- The design references are `design/Homepage.png`, `design/Collection.png`, `design/Contact.png` and `design/About.png` (ignore the cart icon in the designs: there is no cart), and for the dashboard `design/admin-orders.png`, `design/admin-order-detail.png`, `design/admin-products.png`, `design/admin-delivery.png`, `design/admin-dashboard.png` and `design/admin-login.png` (see "Admin design system"). Read the relevant one before any UI work.

## Stack

- **Monorepo:** pnpm workspaces
  - `frontend/`: Next.js (App Router), TypeScript, Tailwind CSS v4, TanStack Form, TanStack Query
  - `backend/`: Express 5 + TypeScript, MongoDB (Atlas) with Mongoose, run with `tsx`
  - `shared/`: Zod schemas, inferred types, constants, helpers (pricing, collection filters), API request/response shapes, mock data
  - `config/eslint/`: shared ESLint flat config (`/base`, `/next`)
- **Validation:** Zod v4. **All schemas live in `shared/`** and are used by both the frontend forms and the backend. Never redefine a schema or type in an app; import it from `@rassm/shared`.
- Mock data (`@rassm/shared/mocks`, parsed through the schemas at load time) is used **only by the seed script and the tests**. The site reads everything from the API.
- TypeScript is pinned to `~6.0` because typescript-eslint does not support 7.x yet.
- Next.js is v16 (Turbopack, `next lint` removed, ESLint runs directly). Read `frontend/AGENTS.md` and the docs in `frontend/node_modules/next/dist/docs/` before using a Next API you are unsure about.
- `@rassm/shared` ships TS source with extensionless imports. It runs through Next (`transpilePackages`) or `tsx`, not plain `node`.

## Business rules

### Exchange policy (the "Échanges" page, `/echanges`)

- The exchange must be **requested on the day of delivery**.
- The product must be **unworn and in its original condition**.
- The **customer pays the delivery costs** of the exchange.
- If the product does not come back in the same condition, there is **no exchange**: the same product is sent back to the customer.
- Wherever the site mentions exchanges, say "Échange possible le jour de la livraison" and link to `/echanges` (`routes.exchanges`). Today: the product page reassurance line, the note under the order button, the size guide and the FAQ. The `/echanges` page writes the four rules as numbered steps with a WhatsApp button "Demander un échange" (prefilled message, `whatsappLink` from `content/contact.ts`); keep it in sync with these rules.

### Delivery fees and stop desk

- `WILAYAS` holds the **58 official wilayas** (codes 01 to 58), the list Anderson uses. The wilayas created in 2025 (Aflou, Barika, Bou Saâda…) are deliberately not in the list.
- Each wilaya has a `homePrice`, a `stopDeskPrice` and `estimatedDays` (delivery time from Alger). `stopDeskPrice: null` means **no stop desk, home delivery only**. Today that applies to Tindouf (37), Bordj Badji Mokhtar (50), Béni Abbès (52) and In Guezzam (54).
- Use `getAvailableDeliveryTypes(fee)` to decide which delivery options to show. `getDeliveryPrice` and `getDeliveryFeeWithDiscount` throw `DeliveryTypeUnavailableError` (French message) for stop desk in those wilayas. The backend must turn it into a 400 error and never accept such an order.
- Mock fees (`shared/src/mocks/delivery-fees.ts`) are the real **Anderson rates, departure Alger**, e.g. Alger 400 home / 250 stop desk, 1 day. The highest home price is Djanet (1,800 DA), which is the limit for discount tier amounts.
- **Prices are edited in the dashboard** (`/admin/livraison`): home and office prices (positive whole DA), delay, stop desk on/off (`stopDeskPrice: null`), and **`suspended`**: a suspended wilaya is shown disabled in the order form ("Livraison temporairement indisponible", `WILAYA_SUSPENDED_LABEL`), marked on `/livraison`, and the API refuses its orders (400 under `wilayaCode`, `WILAYA_SUSPENDED_MESSAGE`; an admin edit that keeps the order's wilaya is allowed). A price change that would make a product tier invalid (amount not lower than the new highest home price) is shown as a warning before saving (`?apercu=1` preview), never silently. `pnpm seed` only adds missing wilayas (it never overwrites edited prices, except `--reset`).
- **Regions** (dashboard tabs, `region` on each wilaya in `WILAYAS`, `REGION_LABELS`): four regions. Centre = Alger, the central coast, Kabylie, Médéa and Aïn Defla (06, 09, 10, 15, 16, 26, 35, 42, 44); Est = the north-east with M'Sila (04, 05, 12, 18, 19, 21, 23, 24, 25, 28, 34, 36, 40, 41, 43); Ouest = the north-west with Chlef, Tiaret and Tissemsilt (02, 13, 14, 20, 22, 27, 29, 31, 38, 46, 48); Sud = the Sahara, its gates (Laghouat, Djelfa, Biskra, El Bayadh, Naâma) and the new wilayas (01, 03, 07, 08, 11, 17, 30, 32, 33, 37, 39, 45, 47, 49 to 58).

### Quantity-based delivery discount tiers (per product)

- Each product has `deliveryDiscountTiers`: up to **5** tiers, empty by default (empty = no discount). Each tier has a `minQuantity` (integer, at least 1) and is either `{ type: "amount", amount }` (DA, integer, more than 0) or `{ type: "free" }` (free delivery).
- Validation (French errors): no two tiers with the same `minQuantity`, at most 5 tiers, **strictly increasing tiers** (sorted by `minQuantity`, each tier gives more than the previous one, and a `free` tier can only be the last), and every amount **lower than the highest home delivery price**. Validate with `createProductSchema(getMaxHomeDeliveryPrice(deliveryFees))`. The limit always comes from the fee data, **never hard-coded**.
- Discounts reduce the **delivery fee only, never the product price**. They apply to both home delivery and stop desk.
- **Calculation**, always with `getDeliveryFeeWithDiscount({ wilayaCode, deliveryType, items, products, deliveryFees })` from `@rassm/shared`. Never reimplement it.
  1. For each distinct product, add up its quantity across all sizes.
  2. Its applicable tier is the one with the highest `minQuantity` ≤ that quantity. No match = no discount from that product.
  3. If any product's applicable tier is `free`, the whole delivery is free.
  4. Otherwise the amounts of all products **add up**.
  5. The total is capped at the base fee: the final fee **never goes below 0 DA**.
- It returns `deliveryFeeBase`, `deliveryDiscount` (applied), `deliveryFee` (final), `freeDelivery`, `deliveryDiscountLines` (per product: product, quantity, tier, amount) and `nextDeliveryDiscountTiers` (per product: units missing to reach the next better tier, and that tier). The next tiers list is empty once delivery already costs 0.
- An order from the product page passes one line: `items: [{ productId, quantity }]`. The helper still accepts several lines (quantities of the same product add up).
- The **backend always recalculates** from the products loaded from the database and the fee table. It never trusts tiers, discounts or delivery amounts sent by the client. The order payload (`productOrderSchema`) carries no price or discount data.
- Orders (`orderSchema`) store one `item` (product id, name, slug, image, color, size, quantity, unit price) plus `deliveryFeeBase`, `deliveryDiscount`, `deliveryFee`, `freeDelivery` and `deliveryDiscountLines`. Order checks: `subtotal = unitPrice × quantity`, `deliveryFee = deliveryFeeBase − deliveryDiscount` (never negative), the discount matches the lines, `freeDelivery` is true exactly when a free tier applied, and `total = subtotal + deliveryFee`.

### Order confirmation (phone call first, no order number for customers)

- A new order has the status `pending` and is **"reçue" (received)**, never "confirmée". It is **confirmed only after our phone call** (we check the product, the size and the address, then the status becomes `confirmed`). Customer texts must never say the order is confirmed before that call.
- **The customer never sees an order number**: not on `/merci` (the URL has no query string), not in the FAQ, the delivery steps, the form notes or the metadata. `orderNumber` (`RSM-000123`, from an atomic counter) exists **internally only**, for the admin dashboard: the API never sends it to the browser. The browser receives the order summary (`orderSummarySchema`: the order without id and number) and an `eventId` (the internal order id), used only as the Meta event id.
- `/merci` says "Merci, votre commande est bien reçue. Nous vous appellerons très bientôt pour la confirmer. Gardez votre téléphone à portée de main.", keeps the order summary (product, color, size, quantity, delivery, total) and reads the last order saved on the device (`getLastOrder`). A customer who needs to change an order contacts us by WhatsApp with their name and product.

### Order form (product page)

- Schemas in `shared/src/schemas/product-order.ts`: `productOrderSchema` (the payload the API validates, inside `orderRequestSchema`) and `productOrderFormSchema` (same rules for the form, whose wilaya select and size start empty; its output is a `ProductOrder`). Customer fields and the "address required for home delivery" rule come from `customer.ts`.
- Fields: Nom complet, Numéro de téléphone (05/06/07 + 8 digits, spaces allowed), Wilaya (58, `formatWilaya`, hint for the new wilayas, "Livraison estimée : N jours"), Commune, Mode de livraison ("À domicile" / "Au bureau" with the price of each; "Au bureau" hidden where `getAvailableDeliveryTypes` has no stop desk, and the choice falls back to home), Adresse (required for home delivery only). Color, size and quantity come from the selectors above the form and are part of the same form.
- Color: required when the product has several colors, selected automatically when it has one. A color can have its own `images`; the gallery then shows them.
- Size: once a color is chosen, the sizes show that color's stock (sold out = crossed out, "Plus que X en stock" from 3). Before a color is chosen, a size is crossed out only if it is sold out in every color. Changing color unselects the size if it is sold out in the new color.
- Quantity: 1 to `min(stock of the variant, 5)` (`MAX_QUANTITY_PER_ORDER`). A suspicious order (see Backend > Fake orders) is limited to 3 units.
- Under the button: "Échange possible le jour de la livraison" and a small link to `/confidentialite` (`routes.privacy`, the French privacy page; keep it in sync with what the site collects, to be reviewed with a legal advisor, see `docs/TODO.md`).
- The form uses `createProductOrderFormSchema(product)` and the submit `createProductOrderSchema(product)`: the shared rules plus `refineVariantStock` (color exists, variant not sold out, quantity ≤ variant stock), with French errors under the color, size or quantity.

### Stock per variant (color + size)

- Stock lives on each color: `colors: [{ name, hex, images?, stock: { S, M, L, XL, XXL } }]`. A variant is one color × one size. A product with one color has one stock table. There is no product-level `stock` field.
- Every color must give a stock for all five sizes (0 = not sold or sold out); missing or invalid values get French errors per size.
- Read stock only with the shared helpers: `getVariantStock(product, color, size)`, `getSizeStock(product, size)` (all colors) and `isProductInStock(product)`.
- Collection filters: a size filter matches a product that has stock in that size **in one of the filtered colors** (any color when no color is filtered).
- **Backend:** the stock is stored per variant on the product (same structure). Each order is validated with `createProductOrderSchema(product)` against the product loaded from the database, then the stock of the ordered variant is **decremented atomically** (`reserveStock` in `backend/src/services/orders.ts`: one `updateOne` whose filter only matches when `colors.$elemMatch { name, stock.<size> ≥ quantity }`, with `$inc` on `colors.$.stock.<size>`), so two orders can never sell the same last unit; when it does not match, the API answers 409 with the French stock error under the size or quantity. If saving the order fails, the units are given back. **Dashboard step:** restore the stock when an order is cancelled or returned.
- Live summary above the button: price × quantity, delivery fee, discount line or "Livraison gratuite", total, and the next-tier hint (`formatNextTierMessage`: "Ajoutez 1 article pour la livraison gratuite"). Before the wilaya is chosen it uses `getDeliveryDiscountProgress`.
- "Confirmer la commande" is disabled while sending and a second click is ignored (one order only). Invalid submit: French error under each field, then scroll to and focus the first invalid field (color and size first).

The product page shows the product's tiers in French ("1 article : −100 DA · 2 articles : −200 DA · 3 articles : livraison gratuite").

### Order statuses, stock and blacklist (dashboard)

- Statuses: `pending` (Reçue, "Nouvelles" tab) → `confirmed` → `shipped` → `delivered`; `cancelled` and `returned` close it. Allowed changes only (`ORDER_STATUS_TRANSITIONS` in `shared/src/schemas/admin.ts`): pending → confirmed / cancelled; confirmed → shipped / cancelled; shipped → delivered / returned; delivered → returned; cancelled → pending (reopen). Never "livrée" before "expédiée".
- **Stock:** the units are taken when the order is placed (`stockReserved: true`; orders saved before the dashboard have no flag and count as holding their units). Cancelled or returned → given back **exactly once** (the flag flips atomically first, so double clicks or repeated changes never give them back twice). Reopening a cancelled order takes them again if they are still in stock (otherwise a French 409).
- **Edits** are allowed while `pending` or `confirmed` (after the call: other size, color, quantity, wilaya, commune, address, delivery type, name, phone). Every amount is recomputed with the shared helpers (unit price kept as agreed, tiers and fees from the database), and the stock moves atomically: the new variant is taken first, the old one given back once the order is saved. Each edit is written in the history ("Taille M → L, Total 7 200 DA → 14 000 DA").
- Every change (creation, status, edit, blacklist) is in `history` with date, time and admin e-mail. `adminNote` is a free internal note. `openedAt` (null = "Nouveau" badge) is set when an admin opens the order.
- Confirming an order sends the Meta server event **ConfirmedOrder** once per order, in the background (see Backend > Meta Conversions API). "Marquer comme commande de test" in the order's "⋯" menu (`test`, `PUT /orders/:id/test`, grey "Test" pill) keeps an order out of it. **Test orders** are only shown in the orders list (grey pill, "Commandes de test" filter, `?tests=1`); every statistic, the best sellers, the clients (list, detail, search, CSV), the products' order counts and the Anderson export leave them out (`REAL_ORDERS` in `models/order.ts`: add it to the first `$match` of any new query over orders).
- **Blacklist** (`Blacklist` model, phone + French reason): new orders from these numbers are still saved, but flagged "Liste noire" (red) in the dashboard and the e-mail. Checked when orders are read, so removing a number removes the flag.
- **Anderson export:** confirmed orders (chosen, or all) as a CSV for Excel (UTF-8 BOM, `;`): Référence, Nom, Téléphone (with spaces so Excel keeps the 0), Wilaya, Commune, Adresse ("Stop desk (bureau Anderson)" for stop desk), Type de livraison (Domicile / Stop desk), Produit, Montant à encaisser (DA). Then "Marquer expédiées" ships the exported orders in one action.
- **Bulk "Annuler"** (orders list, selected orders, `POST /orders/cancel`): cancels the new and confirmed ones after a confirmation dialog (others skipped), stock given back once each. It is never automatic: a "Suspecte" order may be a real customer, so call first (see Security).
- **Team alerts** (`services/alerts.ts`, `notifications/alert-email.ts`, e-mail to `NOTIFY_EMAIL`, background): one IP crossing 5 orders or 15 units in 24 h (once per IP per day), and a size losing more than half of its stock within an hour (at least 3 units, once per size per hour). Each says to call before cancelling.
- **New order e-mail** (Brevo, `backend/src/notifications/new-order-email.ts`): sent in the background for each real new order (never for a honeypot or a duplicate) to `NOTIFY_EMAIL`, in French (customer, phone, wilaya, commune, product, color, size, quantity, total, flags, button to the order). A Brevo failure is logged and stored on the order (`emailNotification.status`), never failing the order.

### Products in the dashboard (step 3C)

- **SKU** (`sku`, `skuSchema`): readable and unique, made by the API from the category (`RSM-H-001` hoodies, `RSM-S-` sweatshirts, `RSM-T-` t-shirts, next free number; `nextSku`), never typed by hand and never changed (even if the category changes). Products saved before step 3C get one when the API starts (`ensureProductSkus`, safe to re-run). The Anderson export puts it before the product name.
- **Form** (`adminProductInputSchema` / `createAdminProductInputSchema(maxHomeDeliveryPrice)`, TanStack Form, French errors under each field, server errors too): name, slug (from the name with `slugify`, editable, unique: 409 under `slug`), description, category, price, drop ("Drop 001"), colors (name + swatch, up to 8), **photos per color** (at least 1, up to 12; the first is the main photo; the product's `images` = the first color's photos), stock grid per color × size, the tier editor "Réductions sur la livraison" with a live preview identical to the product page, switches "Visible sur le site" (`isActive`) and "Mis en avant" (`featured`). Saving sends the `updatedAt` read with the product: if it changed meanwhile (an order took stock), the API answers 409 and the admin reloads. Leaving with unsaved changes asks for confirmation.
- **Status** (`getProductStatus(product, lowStockThreshold)`): Masqué (hidden) / Rupture (total stock 0) / Stock faible (**total stock** of all colors and sizes at or below the threshold) / Actif; stock dot green / ochre / red. The threshold (default 10, `DEFAULT_LOW_STOCK_THRESHOLD`) is a dashboard setting stored in the database (`Setting` model, `GET|PUT /api/admin/settings`, button "Seuil de stock faible" on the products page). A variant with 1 to 3 units (`LOW_VARIANT_STOCK`) is only highlighted in ochre inside the stock grid, never as a product status.
- **Duplicate:** hidden copy, "(copie)" in the name, new slug (`-copie`, `-copie-2`…), new SKU, stock at 0, same photos.
- **Delete / hide:** a product with orders can only be hidden (orders keep their data); a product without orders can be deleted after confirmation. Hidden products are absent from the collection and their page is the French 404; out-of-stock products stay visible (sizes crossed out).
- **Photos** (Cloudinary, `backend/src/services/image-storage.ts`): uploaded through the API (`POST /api/admin/uploads`, signed, the secret never reaches the browser), JPG / PNG / WebP only (checked from the file's bytes), 8 MB max, metadata removed before upload (`lib/image-metadata.ts`: EXIF with GPS, XMP, IPTC, comments; the JPEG orientation is kept), stored resized to 2 000 px and compressed as WebP; next/image serves them (`images.remotePatterns` in `next.config.ts`). A photo is deleted from Cloudinary when nothing uses it any more: removed from a product (on save), removed in the form before saving, or its product deleted, but never while another product (a duplicate) or an order still uses it.
- **Public pages refresh at once** after any product or delivery change: the API calls the website's `POST /api/revalidate` (secret header `x-revalidate-secret`, `REVALIDATE_SECRET` in both apps), which revalidates the cache tags `products` / `delivery-fees` used by `apiGet` (`{ expire: 0 }`: the next visitor gets fresh data).

### Statistics, profit and ads (step 3D)

- **Every number comes from MongoDB aggregations** over the stored orders, products and ads spend (`backend/src/services/admin-stats.ts`): never an estimate or a placeholder. Every statistic has an "ⓘ" (`InfoTip`) explaining in French how it is calculated; keep it in sync with the formula.
- **Period**: Algerian calendar days (UTC+1, `rangeInstants`, `algiersDate`), orders counted by their **order date**. Presets Aujourd'hui, 7 jours, 30 jours (default), Ce mois, Cette année, Personnalisé (`presetRange`; in the URL `?periode=` or `?du=&au=`). The chart is per day up to 31 days, per week (Monday) up to 183, per month beyond (`granularityFor`, `bucketsOf`).
- **Trends** compare with the previous period of the same length (`previousRange`, `trendPercent`): hidden when that period had no orders (`hasPrevious`) or the previous value is 0.
- **Chiffre d'affaires encaissé** = `subtotal` (articles, without delivery: the delivery fee goes to Anderson) of the **delivered** orders; **en attente** = confirmed + shipped.
- **Bénéfice net** = Σ delivered (`subtotal` − `unitCost` × quantity − `deliveryDiscount` − packaging) − Σ returned (return cost + packaging) − ads spend of the period. Margin = bénéfice ÷ encaissé. A delivered order without cost price counts no product cost and is listed in the "coût manquant" warning (link to the products).
- **Cost snapshots**: the product's `costPrice` (Prix de revient, optional, admin only: never in the public API or the order summary) is copied on the order (`item.unitCost`) when it is placed and kept on admin edits; the packaging and return costs (Paramètres, `Setting` model) are copied on the order (`costs.packaging`, `costs.returnCost`) when it becomes delivered or returned. Orders closed before step 3D use the current settings.
- **Rates**: confirmation = orders **ever confirmed** (status now confirmed or later, or a `confirmed` step in `history`, so an order cancelled or returned after the call still counts) ÷ every order except pending, with "Annulées après confirmation" (cancelled orders that had been confirmed) under it; delivery = delivered ÷ (delivered + returned). Réductions livraison = Σ `deliveryDiscount` and count of `freeDelivery` on delivered orders.
- **Ads spend** (`AdSpend` model, `/admin/publicite`): a day or a period (`startDate`–`endDate`, whole DA, note), **spread evenly per day** (`spendPerDay`): a range only counts its own days. Coût par commande = spend ÷ orders, par commande livrée = spend ÷ delivered, ROAS = encaissé ÷ spend (`toAdSpendSummary`; null when nothing to divide, shown "—").
- **Best sellers**: units of confirmed, shipped and delivered orders per product + color; profit of the delivered units (null when one has no cost); current stock of that color.
- **Clients** (`services/admin-clients.ts`): orders grouped by phone (one phone = one client), name and wilaya of the latest order, spent = totals of delivered orders. Badges: Liste noire, Fidèle (≥ 3 delivered, `LOYAL_DELIVERED_ORDERS`), À risque (≥ 1 returned).
- **Messages**: opening one marks it read; "Suspect" pill (`suspicious`, `suspiciousReason`) for messages sent in under 2 seconds or without the form; unread counter (not archived) on "Messages" in the sidebar, the phone "Plus" tab and the bell (new orders and unread messages grouped), polled with `/orders/updates` (`unreadMessages`). A new contact message sends a French e-mail to `NOTIFY_EMAIL` (Brevo, `notifications/new-message-email.ts`, background, result stored on the message).
- **Newsletter** (`services/newsletter-sync.ts`), **double opt-in**: a new sign-up gets a French confirmation e-mail through Brevo (`notifications/newsletter-confirm-email.ts`) with a link `/newsletter/confirmation#jeton=…` (token in the fragment, only its SHA-256 stored, 7 days, single use, a new e-mail at most once an hour); the page posts it to `POST /api/newsletter/confirm`, and only then is the address added in the background to the Brevo list `BREVO_NEWSLETTER_LIST_ID` (`confirmationPending` absent = confirmed; sign-ups from before the double opt-in count as confirmed). Sign-ups sent too fast get no e-mail ("En erreur" with the reason). Deleting a subscriber in the dashboard removes it from the list. The status is stored per subscriber (À confirmer with "Renvoyer l'e-mail" / Synchronisé / En erreur with "Réessayer" / En cours / Non configuré). Without Brevo on a local computer, the link is written in the API logs. Newsletters are written and sent from Brevo.

## Backend (`backend/src/`)

- `server.ts` (entry: env, MongoDB, listen; `connectDatabase` in `db.ts` retries the Atlas SRV lookup with `DNS_FALLBACK_SERVERS` when the computer's DNS refuses it, e.g. behind a VPN), `app.ts` (`createApp(options)`: helmet, CORS limited to `FRONTEND_ORIGIN`, JSON body limit 20 kB, NoSQL key guard, routes, 404, error handler), `env.ts` (Zod validation of the environment at startup, see `backend/.env.example`), `db.ts`, `seed.ts` + `seed-cli.ts` (`pnpm seed`).
- `models/`: Mongoose models matching the shared schemas: `Product` (`_id` = the shared id, e.g. `prod_001`; stock per color + size), `DeliveryFee` (58 wilayas), `Order`, `ContactMessage`, `NewsletterSubscriber` (unique email), `Counter` (order numbers), `Setting` (dashboard settings: low stock threshold, packaging and return costs), `AdSpend` (ads spend). `toProduct`, `toOrderSummary`, `toOrder` convert documents to the shared types and validate them, so the API always answers in the shared shapes.
- Public API (paths in `API_PATHS`, `shared/src/schemas/api.ts`): `GET /api/products` (same query parameters as the collection page: `category`, `color`, `size`, `min`, `max`, `sort`; uses the shared `parseCollectionFilters` / `filterAndSortProducts`), `GET /api/products/:slug`, `GET /api/delivery-fees`, `POST /api/orders`, `POST /api/contact-messages`, `POST /api/newsletter`, `POST /api/newsletter/confirm`, `GET /health`. **Public products never carry the exact stock or the SKU** (`toPublicProduct`, `publicProductSchema`): each size is `available`, `low` with its number (3 or less, `PUBLIC_LOW_STOCK`) or `sold_out`; the shop pages turn it back into a `Product` with `fromPublicProduct` ("available" = `MAX_QUANTITY_PER_ORDER` units), so pickers work as before and the API checks the real stock on every order.
- **Errors:** every body is validated with a shared schema (`parseOrThrow`). Errors the client may see are `HttpError` (status + French message + French `fields`), answered as `{ error: { message, fields? } }` (`apiErrorSchema`). Anything else is logged (English) and answered with a generic French 500 (503 "Le service est momentanément indisponible." when MongoDB cannot be reached): internals never leak.
- **Order flow** (`services/orders.ts`, `placeOrder`): validate → load the product → `createProductOrderSchema(product)` → price with `getDeliveryFeeWithDiscount` and the fees from the database → honeypot → duplicate check → phone limit → fraud checks and flags (`assessOrder`) → atomic stock decrement → order number → save (`pending`, with client IP and user agent, Meta cookies) → Meta Purchase (not for bots), the e-mail and the alerts in the background → `201 { order, eventId }`.
- **Fake orders** (`services/fraud.ts`): phones are normalised before every check (`normalizeAlgerianPhone` in `algerianPhoneSchema`: spaces, dashes, `+213` / `00213`, Arabic digits → `0555123456`); rate limit per IP (orders 30, contact 5, newsletter 10 per 15 min, French 429) and at most 5 orders per phone in 24 h (`MAX_ORDERS_PER_PHONE_PER_DAY`, 429 under `phone`); honeypot `website` (order, contact and newsletter forms) filled → same success answer, nothing saved, no stock taken; same phone + same product within 30 min (not cancelled) → nothing created, and the answer repeats the summary of what was just sent with a new random id (never the stored order or its id); from the 3rd order of a phone, beyond 5 orders or 15 units from one IP in 24 h (`SUSPICIOUS_ORDERS_PER_IP`, `SUSPICIOUS_UNITS_PER_IP`, plus a team alert), or a form sent in under 2 seconds or without the form (`elapsedMs`, `formTimingReason`, `MIN_FORM_FILL_MS`), the order is saved with `suspicious: true` and a French `suspiciousReason`; a suspicious order still reserves its stock but holds at most 3 units (`MAX_SUSPICIOUS_ORDER_QUANTITY`, 409 under `quantity`). **Many mobile customers in Algeria share one IP (carrier-grade NAT): IP rules must never block normal customers.** The only IP refusal is beyond 60 units in 24 h (`MAX_UNITS_PER_IP_PER_DAY`, cancelled orders not counted, French 429). Contact messages get the same time check (`suspicious`, "Suspect" in Messages); fast newsletter sign-ups are kept but not sent to Brevo (status "En erreur" with the reason; "Réessayer" sends them).
- **Security** (see `docs/SECURITY.md`): helmet with a JSON-only policy (`default-src 'none'`, HSTS, `no-referrer`); rate limits on every route (`DEFAULT_RATE_LIMITS` in `app.ts`: global, catalog, forms, login, password, admin, and `sensitive` for uploads and CSV exports); logs go through `lib/logger.ts`, which masks phone numbers and removes addresses, passwords, tokens, keys and connection-string credentials (also inside error messages): never `console.log` customer data; production refuses weak, example or non-https values (`env.ts` `superRefine`, `weakSecretReason`), and needs `TRUST_PROXY` and `ADMIN_PROXY_SECRET`; an https `FRONTEND_ORIGIN` without `NODE_ENV=production` is refused (forgetting it never lowers the guard); `NOTIFY_EMAIL` and `EMAIL_FROM` have no default (required with `BREVO_API_KEY`); `META_TEST_EVENT_CODE` in production prints a loud warning at startup. Reset and newsletter links are written in the logs (no Brevo) only when `ADMIN_URL` is localhost. Backups: `backup.ts` + `backup-cli.ts` / `restore-cli.ts` (canonical Extended JSON lines, gzip, AES-256-GCM with `BACKUP_PASSPHRASE`; production refuses an unencrypted backup unless `pnpm backup -- --unencrypted`).
- **Client IP** (`lib/client-ip.ts`): public routes use `req.ip`, which reads `X-Forwarded-For` only for the `TRUST_PROXY` proxies of the host (never trusted from the local machine as such). Dashboard routes (`/api/admin`, reached through the website) ignore `X-Forwarded-For` (Next.js passes on the one a visitor writes): the website's `proxy.ts` sends the visitor IP in `x-rassm-client-ip`, signed with `ADMIN_PROXY_SECRET` (`signClientIp`, HMAC-SHA256 with the time, 60 s at most); without a valid signature the connection's address is used. Limits, locks, sessions and alerts use `clientIpOf`.
- **Password checks** (`lib/password.ts`): at most 3 at once (`MAX_CONCURRENT_PASSWORD_CHECKS`, 64 MiB each), beyond that a French 503 at once (`PasswordBusyError`). Logins are also limited for every IP together (`loginAll`, 100 per 15 min), except from a browser an admin already logged in with (`knownDevice`).
- **Data retention** (`services/data-retention.ts`): IP addresses and browsers kept with orders, contact messages and newsletter sign-ups are deleted 12 months after them (the API runs it at startup and daily; `pnpm purge-client-data`). The privacy page states it.
- **Meta Conversions API** (`meta/conversions-api.ts`): only when `META_PIXEL_ID` and `META_CAPI_ACCESS_TOKEN` are set. Purchase with `event_id` = order id (same as the browser), `action_source: website`, hashed (SHA-256) phone `213…`, first and last name, wilaya as city, country `dz`, plus IP, user agent, fbp, fbc; value + `DZD`. Sent in the background, the result is stored on the order (`metaPurchase.status`: sent / failed / skipped); a failure is logged and never fails the order. **Never sent for a bot** (a form sent too fast or without the site's form, `formTimingReason`; a honeypot or a duplicate creates no order at all): stored "skipped" with "robot probable…", shown "Non envoyé : …" in the order. Other suspicious orders are still sent. **ConfirmedOrder** (`services/meta-confirmed.ts`, `buildConfirmedOrderEvent`): when the team confirms an order by phone, one server event `ConfirmedOrder` (custom event, `event_id` = `<order id>:confirmed`, `action_source: website`) with exactly the Purchase customer data (same `buildUserData`, the order's original fbc / fbp, IP and user agent), the order's current total and `DZD`; `META_TEST_EVENT_CODE` applies like for Purchase. Sent **once per order**: the state is on the order (`metaConfirmed`: waiting / sending / sent / failed / skipped, `confirmedAt`, `at`, `detail`) and every step is an atomic update, so confirming again after a cancel or a reopen never sends it twice. Never sent for a test order or a blacklisted number (skipped with the reason). A suspicious order waits ("waiting") and is sent only once shipped, with the confirmation time (a recent time if older than Meta's 7 days), so a suspicious order cancelled after the call never reaches Meta. In the background: a Meta failure is logged and stored ("failed"), never blocks the status change. Shown in the order's "Informations internes": "Envoyé à Meta le …" / "Échec le …" / "Non envoyé : …".
- **Seed:** creates missing products and wilayas; existing products and delivery prices are never overwritten (real stock and dashboard edits are kept) unless `pnpm seed --reset`. It also gives SKUs to products without one.
- **Tests** (`backend/test/`): Vitest + Supertest + mongodb-memory-server (one in-memory MongoDB, cleaned and re-seeded before each test, Meta mocked). Cover server-side pricing and discount tiers, ignored client prices, atomic stock, stop desk refused in Tindouf, honeypot, duplicates, fraud flags, rate limits, French validation errors, NoSQL injection, CORS, the Conversions API payload, the site-wide hardening (`hardening.test.ts`: CSRF, headers, every admin route behind a session, time check, phone normalisation, upload types and metadata, private fields never public, rate limits, log masking, production env, backup and restore), the independent review fixes (`review-fixes.test.ts`: forged `X-Forwarded-For`, signed IP, IP rules, alerts, bulk cancel, bots and Meta, known browsers and the lock, password slots, reset queue, data retention, newsletter link expiry, backups), and the admin account security (`admin-security.test.ts`: 5-attempt lock per account and per IP with doubling, sessions and remember me, revocation, password change and reset, alerts with a mocked Brevo).

### Admin API (`/api/admin`, `backend/src/routes/admin.ts`)

- **Login and account security** (`routes/admin-auth.ts`, `services/admin-auth.ts`, `services/login-throttle.ts`): `POST /auth/login` (shared `adminLoginSchema`, `remember` = "Se souvenir de moi"), `POST /auth/logout`, `GET /auth/me`, `POST /auth/password/forgot`, `POST /auth/password/reset`.
  - **Lock**: 5 failed logins in a row (`MAX_FAILED_LOGINS`) lock the account **and** the IP that made them (`LoginThrottle` model, keys `account:<e-mail>` and `ip:<address>`, also for e-mails that do not exist, so a lock never reveals which accounts exist). 15 minutes, doubled at each new lock (30 min, 1 h…) up to 24 h (`lockMinutes`); forgotten 24 h after the last failure or lock; a successful login or a password reset clears it. While locked: 429 "Trop de tentatives. Réessayez dans X minutes." (`formatLockMessage`) and nothing else, even with the right password. Wrong e-mail and wrong password get the same message, timing and locks. **A browser the admin already logged in with** (its `rassm_device` cookie in `Admin.knownDevices`) is only stopped by its own IP lock, never by the account lock, so nobody can keep the admin locked out. A wrong current password in "Changer le mot de passe" counts as a failed login; when it locks the account, that session is closed (stolen session). On top of that Express limits per IP (20 logins, 10 per password route, per 15 min) and for every IP together (see Security).
  - **Sessions** (`AdminSession`, server-side so they can be revoked): random token in the `rassm_admin` cookie (`__Host-rassm_admin` in production, `adminCookieName`: host-only, Secure, path "/", never shared with a subdomain; httpOnly, SameSite=Strict), only its SHA-256 stored, a new token on every login (the previous one of the browser is deleted: no session fixation). Without "Se souvenir de moi": browser-session cookie, 12 hours at most and 2 hours without activity (`lastActivityAt`, written at most once a minute). With it: 30 days on that device. Device, browser, IP and approximate location are kept for the Sécurité page.
  - **Passwords** (`lib/password.ts`): argon2id (Node `crypto.argon2`, 64 MiB, 3 passes; the tests use a lighter cost), old scrypt hashes still verified and replaced at the next login. Rules (`adminPasswordSchema`): 12 characters minimum, not containing "rassm", not a common password (`isCommonPassword`: list + common words once digits, symbols and leetspeak are removed).
  - **Reset by e-mail**: "Mot de passe oublié ?" always answers `FORGOT_PASSWORD_MESSAGE` ("Si ce compte existe, un e-mail a été envoyé…"); for a real admin a random token (only its SHA-256 stored, `AdminPasswordReset`) is sent through Brevo as `ADMIN_URL/nouveau-mot-de-passe#jeton=…` (in the fragment: never sent to a server), valid 30 minutes, single use, only the latest link works, 3 e-mails per account per hour. The answer is sent at once and the requests are handled one after the other afterwards (same timing for every e-mail; the hourly limit holds even for requests sent together). It works while the account is locked; a reset sets the password, logs out every session and unlocks the account and the IP. Without Brevo on a local computer the link is written in the API logs.
  - **Alerts** (`notifications/security-email.ts`, `SecurityMailer`, Brevo, to the admin's own address, in the background): login from a new browser (random `rassm_device` cookie, httpOnly, 400 days; its hash in `Admin.knownDevices`; not for the very first login of an account), password changed or reset, account locked. Each gives the date, time (Algeria), device, browser, approximate location and IP, and a link to `ADMIN_URL/parametres#securite`.
  - **Approximate location**: from the host's geolocation headers (Cloudflare `cf-ipcity` / `cf-ipcountry`, Vercel `x-vercel-ip-*`), "Réseau local" for private IPs, otherwise unknown. No IP is sent to a third-party service.
- Everything else requires a session (`requireAdmin`, 401 "Veuillez vous connecter."). Every change (POST, PUT, PATCH, DELETE) must come from the dashboard's origin (`ADMIN_ORIGIN`, else `FRONTEND_ORIGIN`; `requireSameOrigin`: `Origin` required and allowed, `Sec-Fetch-Site` not cross-site) **and** carry the session's anti-CSRF token in `X-CSRF-Token` (`requireCsrfToken`; token = HMAC of the session token, given in the answers of the login and of `GET /auth/me`, **never in a cookie**: `lib/data/admin.ts` keeps it in memory, fetches it from `/auth/me` after a reload, and retries once with a fresh one when the API answers `CSRF_REFUSED_MESSAGE`). Answers are `Cache-Control: no-store`: `GET /search?q=` (top bar: 5 orders by name, phone or internal number, and 5 products), `GET /orders` (tabs, counts, search by name, phone or order number "RSM-000123" / "123", wilaya, dates, numbered `page` or cursor), `GET /orders/updates?since=` (live polling), `GET /orders/:id` (marks it opened, returns the product for edits), `PATCH /orders/:id` (edit), `POST /orders/:id/status`, `PUT /orders/:id/note`, `POST /orders/:id/blacklist`, `POST /orders/export` (CSV), `POST /orders/ship`, `POST /orders/cancel` (bulk "Annuler"), `GET|POST /blacklist`, `DELETE /blacklist/:phone`, and Paramètres > Sécurité: `GET /security/sessions`, `DELETE /security/sessions/:id`, `DELETE /security/sessions/others`, `POST /security/password` (needs the current password; logs out the other sessions).
- Products, photos and delivery prices (`routes/admin-catalog.ts`, services `admin-products.ts`, `admin-delivery.ts`, `image-storage.ts`): `GET|POST /products` (list with filters `category`, `q`, `status`, `drop`, `sort`, `page`, `limit`, tab counts, drops and KPIs; create), `GET|PUT|DELETE /products/:id`, `PATCH /products/:id/stock` (stock grid), `PATCH /products/:id/flags` (`isActive`, `featured`), `POST /products/:id/duplicate`, `GET|PUT /settings` (low stock threshold, packaging and return costs; partial updates), `POST /uploads` (one photo, multipart field `image`; 503 in French when the Cloudinary keys are missing), `DELETE /uploads` (`{ url }`), `GET /delivery-fees` (with tier warnings), `PUT /delivery-fees/:code`, `POST /delivery-fees/bulk` (`adjust` ± amount, `suspend`, `reactivate`); `?apercu=1` = preview without saving. The admin router accepts JSON bodies up to 200 kB (public forms stay at 20 kB). KPI trends are only sent when computed from real data (count now against 30 days ago from creation dates); stock and price trends are not kept, so they are null.
- Statistics, ads, clients, messages and subscribers (`routes/admin-insights.ts`): `GET /stats?from=&to=` (the whole Tableau de bord, `dashboardStatsSchema`; last 30 days without a range), `GET|POST /ads`, `PUT|DELETE /ads/:id` (`GET` returns every entry and the figures of the range), `GET /clients` (filters `q`, `wilaya`, `badge`, `sort`, `page`, `limit`), `GET /clients/export` (CSV), `GET /clients/:phone`, `GET /messages` (`folder` inbox / unread / read / archived, `subject`, `q`), `GET|PATCH|DELETE /messages/:id` (`GET` marks it read; `PATCH { read, archived }`), `GET /subscribers`, `GET /subscribers/export` (CSV), `POST /subscribers/:id/sync` ("Réessayer", or a new confirmation e-mail for an address not confirmed yet), `DELETE /subscribers/:id`. The global search (`GET /search`) also returns clients.
- `pnpm sync-newsletter` (`src/sync-newsletter-cli.ts`) adds the confirmed subscribers not yet synchronised to the Brevo list (safe to re-run; never an address not confirmed yet).

- **Dashboard** (`app/admin/`, components in `components/admin/`, French, mobile first): `/admin/connexion` (login, design/admin-login.png: `AuthShell` in `components/admin/auth/` with the photo, the brand column, the card and its black footer. On computers every size is in design pixels × `--u` = min(100vw / 1536, 100svh / 1024) (the design is 1536 × 1024), with px minimums for small texts, so the page keeps the design proportions and fits the window without scrolling (1366 × 768 and up); the card only grows the page if it can no longer fit. Photo: `images/admin/login-bg.jpg` when it exists (framed like the design, model left of centre), otherwise a dark concrete backdrop (`about-values.jpg`) with the model of `collection/collection-hero.jpg` placed between the brand and the card, edges faded. Light sans-serif Montserrat (`authSansFont`, `font-auth`) for the subline, inputs, small links and labels, loaded only on these pages. On phones the photo is a band above the card; `login-form.tsx` with TanStack Form + `adminLoginFormSchema`, show / hide password, "Se souvenir de moi", "Mot de passe oublié ?"), `/admin/mot-de-passe-oublie` and `/admin/nouveau-mot-de-passe` (same layout; reads the token from the fragment, then removes it from the address bar), and in `app/admin/(espace)/` (layout checks the session with the API via `getAdminSession`, else redirect): `/admin` (Tableau de bord), `/admin/commandes` (+ `/[id]`), `/admin/produits` (+ `/nouveau`, `/[id]`), `/admin/clients` (+ `/[phone]`), `/admin/livraison`, `/admin/publicite`, `/admin/messages` (+ `/[id]`), `/admin/abonnes`, `/admin/liste-noire`, `/admin/parametres`. `src/proxy.ts` redirects `/admin/*` to the login page when there is no session cookie (`__Host-rassm_admin` or `rassm_admin`; optimistic check), gives every dashboard page a strict Content-Security-Policy with a fresh nonce (`adminCsp`; the admin layout calls `connection()` so every admin page is rendered per request), and adds to every `/api/admin/*` request the visitor IP signed with `ADMIN_PROXY_SECRET` (`visitorIp` in `lib/client-ip.ts`: the `TRUST_PROXY`-th `X-Forwarded-For` entry from the end, as added by the host's proxies; headers of that name sent by the visitor are replaced). **Dashboard on its own subdomain** (ready, used at deployment: `ADMIN_HOST=admin.rassmstore.live` in the website, `ADMIN_ORIGIN=https://admin.rassmstore.live` and `ADMIN_URL=https://admin.rassmstore.live/admin` in the API): `next.config.ts` (pages) and `proxy.ts` (`/api/admin`) then serve the dashboard only on that host (the public host redirects `/admin` there and answers 404 for `/api/admin`), and the dashboard host sends `/` to `/admin` and any other page back to `NEXT_PUBLIC_SITE_URL`. Its `__Host-` cookies never reach the public site, and the Pixel never runs on it. After login, `?suivant=` only accepts a dashboard path of the site (`safeAdminPath`, `lib/admin/safe-redirect.ts`). Admin pages are noindex (metadata + `X-Robots-Tag` in `next.config.ts`) and never linked from the public site. `src/proxy.ts` forwards `/api/admin/*` to the API (`NextResponse.rewrite` to `API_URL`, else `NEXT_PUBLIC_API_URL`, with the signed IP; done in the proxy itself because headers it adds are only guaranteed to reach a rewrite it makes), so the dashboard calls it on the site's own domain (first-party cookie). Data: `lib/data/admin.ts` (browser, `ApiError` in French, 401 → back to login, a non-JSON 5xx from the Next.js proxy → "Le serveur est injoignable pour le moment.") with TanStack Query (`AdminProviders`). `AdminShell` and the pieces of every page: see "Admin design system". The top bar's right side (`admin-top-bar.tsx`) holds the sound button, the notification bell (red dot while there are unopened new orders; its panel lists the 5 latest, links to the "Nouvelles" tab, offers browser notifications and clears the toasts) and the admin's initial (menu: e-mail, Déconnexion). Toasts appear just under the top bar. Orders list (`orders-page.tsx`): filters, tab and page in the URL (`statut`, `q`, `wilaya`, `du`, `au`, `page`, `par`), "Exporter pour Anderson" (all confirmed) in the header, selected orders exported, marked shipped or cancelled ("Annuler", with a dialog reminding to call a "Suspecte" order first) from the bulk bar. Order detail (`order-detail.tsx`): number, "Reçue le … à …", status pill and "⋯" menu (modifier, export, copy the number, liste noire), Appeler / WhatsApp then only the allowed status changes, then the cards and the history timeline. `LiveOrdersProvider` polls `/orders/updates` every 5 s: toast, short sound (mute button, remembered), counter, browser notification when allowed and the tab is hidden. `AdminDialog` is a bottom sheet on phones. Products (`products-page.tsx`: KPI cards with `KpiCard`, category tabs, search, Statut / Drop / Trier par, table with photo, name + SKU, drop, price, `StockLevel`, `ProductStatusBadge`, edit / duplicate / "⋯" with the stock grid `StockGridDialog`, "Visible sur le site", "Mis en avant", Masquer, Supprimer; filters in the URL `categorie`, `q`, `statut`, `drop`, `tri`, `page`, `par`). Product form: `product-editor.tsx` (loads the product and the fee table for the tier limit) + `product-form.tsx` + `product-photos.tsx` (upload several, drag or arrows to reorder, "Principale", delete). Delivery (`delivery-page.tsx`: KPI cards, region tabs, search, stop desk / statut filters, sort, table with "Non disponible", delay `formatDeliveryWindow` ("24 h" or "Jusqu'à 5 jours"), Actif / Suspendu, edit dialog, "⋯" suspend / reactivate, bulk ± X DA with preview, suspend, reactivate, CSV export, tier warnings). Tableau de bord (`dashboard-page.tsx`, design/admin-dashboard.png): period picker, KPI cards (`StatCard` with a bar sparkline and the trend), "coût manquant" warning, Ventes area chart with the Encaissé / Commandes passées / Bénéfice switch and the status donut (`dashboard-charts.tsx`, Recharts, tooltip on hover, hidden table for screen readers), latest orders, best sellers, Performance and Publicité rows, bottom link cards. Shared statistics pieces in `stats-ui.tsx` (`InfoTip`, `useStatsRange`, `RangePicker`, `StatCard`, `MetricTile`, `LinkCard`, French number formats). Publicité (`ads-page.tsx`), Paramètres (`settings-page.tsx`, with the Sécurité section `security-section.tsx` at `#securite`: open sessions with device, browser, location, last activity, "Déconnecter" and "Déconnecter toutes les autres sessions", and "Changer le mot de passe"; also linked from the avatar menu), Clients (`clients-page.tsx`, `client-detail.tsx`: call, WhatsApp, orders, liste noire), Messages (`messages-page.tsx`, `message-detail.tsx`: call, WhatsApp, "Répondre par e-mail", read / unread, archive, delete), Abonnés (`subscribers-page.tsx`: Brevo status, "Réessayer" / "Renvoyer l'e-mail", CSV, delete). Admin URLs: `lib/admin/routes.ts`; formatting (relative dates, Algeria time, WhatsApp confirmation message): `lib/admin/format.ts`.
- `components/ui/`: building blocks: `Button` (filled or outlined, `surface="dark" | "light"`), `SectionLabel`, `SectionTitle`, `ArrowLink`, `HandQuote`, `Container`, `Logo`, `icons.tsx` (thin line SVG icons). Reuse them; do not restyle buttons or labels by hand.
- `components/about/`: the About page sections (`AboutHero`, `AboutStory`, `AboutValues`).
- `components/info/`: the customer info pages (`/livraison`, `/echanges`, `/guide-des-tailles`, `/faq`, `/confidentialite`). `/confidentialite` (`routes.privacy`, footer "Confidentialité" and a small link under the order button): what is collected (order, contact, newsletter, IP and browser, Meta cookies), why, the Meta Pixel and Conversions API, the providers (Anderson, Meta, Brevo, MongoDB Atlas), how long (IP and browser 12 months), and the rights under Law 18-07 with a WhatsApp link. Update it whenever the site collects or shares something new. `InfoPage` is their shared layout (dark band over concrete with label, title and intro, then the content on bone at reading width), with `InfoSection`, `Prose`, `NumberedSteps`, `InfoNote` and `proseLink`. `DeliveryRates` is the searchable table of the 58 wilayas (data from `getDeliveryRates()` in `lib/data/delivery.ts`, never hard-coded; accent-insensitive search with `matchesSearch` from `lib/search-text.ts`; stacked cards below `md`; delays with `formatDeliveryDelay` from `@rassm/shared`). `FaqAccordion` renders `content/faq.ts` with native `<details>`; `/faq` also outputs FAQPage JSON-LD built from the same content.
- `components/contact/`: the contact page sections (`ContactHero`, `ContactChannels`, `FaqBand`, `BrandLocation`) and `ContactForm`. `components/ui/form-field.tsx`: `FormField` (label, control, hint, French error; `labelStyle="caps" | "plain"`), `inputClasses` and `describedBy`, shared by the order and contact forms.
- `components/layout/`: `SiteHeader` (transparent over the hero on `/`, dark band elsewhere, full-screen menu below `lg`), `SiteFooter`, `NewsletterForm` (TanStack Form + `newsletterFormSchema`, `revalidateLogic`; after sending it asks to confirm by e-mail), `NewsletterConfirmation` (the `/newsletter/confirmation` page, noindex: reads `#jeton=`, removes it from the address bar, calls `confirmNewsletter`).
- `components/home/`, `components/collection/`, `components/product/`: page sections, `ProductCard` / `ProductListItem` (the whole card links to the product page, no "+" button), product gallery, quantity stepper, size guide dialog.
- `components/product/order/`: the product page order. `ProductOrderProvider` owns the TanStack Form (`productOrderFormSchema`, `revalidateLogic`) and shares it through context with `ProductOptions` (color, size, quantity), `ProductOrderGallery` (photos of the selected color), `OrderForm` + `OrderSummary`, and `StickyOrderButton` (mobile only: "Commander maintenant" fixed at the bottom, scrolls to the form, hidden once the form is on screen). The provider also sends ViewContent and InitiateCheckout.
- `app/merci/` + `components/order/OrderReceived`: thank-you page (`/merci`, no query string, noindex): "Merci, votre commande est bien reçue. Nous vous appellerons très bientôt pour la confirmer.", the order summary, link to the collection. It reads the last order saved on the device (`getLastOrder`). Sends Purchase.
- French tier texts come from `formatDeliveryDiscountTiers` / `formatTierBenefit` / `formatDiscount` / `formatNextTierMessage`.
- **Collection filters live in the URL** (`?category=hoodie,tshirt&color=noir&size=M&min=5000&max=8000&sort=price-asc&view=list`). Pure logic in `lib/collection-filters.ts` (parse, serialize, facets, filter and sort, tested). The page updates the URL with `window.history.replaceState` (no server round trip) and reads it with `useSearchParams`; the page awaits `searchParams`, so a shared link is server-rendered already filtered.
- `SiteHeader` floats over the photo on `/`, `/collection`, `/a-propos`, `/contact` and the info pages, `/confidentialite` included (`HEADER_OVER_HERO`). It has no search icon for now (see `docs/TODO.md`), and uses the narrow width on `/collection/*`. `Container size="narrow"` is the shop page width (design/Collection.png).
- `content/`: editorial content that is not API data: `hero-slides.ts` (add a slide = add one entry), `navigation.ts` (menu, footer columns, social links), `contact.ts` (WhatsApp, phone and social links, the single source for them), `size-guide.ts` (placeholder measurements, see `docs/TODO.md`; shown by `SizeGuideTable`, used by both the product page dialog and `/guide-des-tailles`), `faq.ts` (questions and answers, links built from `routes` and `CONTACT`).
- `lib/data/`: the data layer, calling the API through `lib/api.ts` (`apiGet`: server-side fetch cached `revalidate` seconds, 30 s for products, 5 min for delivery fees; `apiPost`: browser POST throwing an `ApiError` with the French message and `fields`). `orders.ts`: `placeProductOrder(order, { website, tracking })` posts `orderRequestSchema` (the customer's choices only, never a price) and keeps the answer (`PlacedOrder`) in sessionStorage; `getLastOrder` reads it back for `/merci`. Server errors with `fields` are shown under the matching form field (`toServerErrors` in `lib/form-errors.ts`, set with `form.setErrorMap({ onDynamic })`), e.g. a variant sold out since the page loaded. The order and contact forms have a hidden honeypot field (`components/ui/honeypot-field.tsx`). `lib/routes.ts`: every internal URL (every route in it exists: never link to a page that is not built). `lib/cn.ts`: class name helper.
- Images live in `frontend/public/images/<section>/`. Placeholders and the photos still needed are listed in `docs/PHOTOS-NEEDED.md`; other open items in `docs/TODO.md`.
- Product packshots are square on cream and shown with `object-contain` in 5:4 tiles. After replacing an image with the same file name, delete `frontend/.next` if the dev server still shows the old one (image cache).
- The only English text on the site is the footer tagline next to the logo (`lang="en"`). The homepage story photos (`images/story/`) have English quotes painted on the wall: their alt texts give the quote in French; replace the photos to remove the English.
- **Meta Pixel** (`lib/analytics/meta-pixel.ts`): loaded only when `NEXT_PUBLIC_META_PIXEL_ID` is set (otherwise no Meta script at all). `fbq("set", "autoConfig", false, PIXEL_ID)` before `init`: no automatic events, no automatic advanced matching (Meta never reads the forms); also keep "Automatic advanced matching" off in Events Manager. Always go through `trackMetaEvent` / `trackPurchaseOnce`. Events: PageView on every page (`MetaPixelPageView` in the root layout), ViewContent on product pages (id, name, price), InitiateCheckout on the first focus in the order form, Purchase on `/merci` (value = order total, `eventID` = the `eventId` returned by the API, once per order, remembered in localStorage). The API sends the same Purchase server-side (Conversions API) with the same event id, so Meta counts it once. **Ad click id**: on every page of the site, `captureAdClick` (called by `MetaPixelPageView`) keeps `?fbclid=` in the `_fbc` cookie (`fb.1.<time>.<fbclid>`, 90 days, unless it already holds that click), so a visitor who lands on one page and orders from another keeps it, even when the Pixel is blocked. The order form sends `_fbp` / `_fbc` and the page URL with the order (`getMetaTracking`; when the Pixel is on but `_fbp` is missing, a blocker, it is created in Meta's format), stored on the order (`tracking`) and sent with Purchase and ConfirmedOrder. Currency `DZD` (`PIXEL_CURRENCY`), kept on purpose: DZD is a supported Meta ad account currency, even though the Pixel script logs a currency warning on Purchase. Duplicate calls caused by React Strict Mode in development are dropped.
- **Security headers** (`lib/security-headers.ts`, applied by `next.config.ts` to every route; the public CSP skips `/admin`): public CSP (scripts from the site and `connect.facebook.net` only, `'unsafe-inline'` because the pages are prebuilt and cached; images from the site, Cloudinary and Meta; requests to the site, the API and Meta; `frame-ancestors 'none'`), `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, COOP, HSTS once `NEXT_PUBLIC_SITE_URL` is https, no `X-Powered-By`. A new third-party script, image host or API domain must be added there. Never use `eval` / `new Function` (Zod runs `jitless` in the browser for this reason, `schemas/common.ts`).
- Public forms send `elapsedMs` (`useFormTimer`, `lib/form-timer.ts`) and the honeypot with `sendContactMessage`, `subscribeToNewsletter` and `placeProductOrder`.
- Animations respect `prefers-reduced-motion` (`motion-safe:` / `motion-reduce:` classes; the hero slider does not auto-play).

## Production hosting

Step-by-step guide: `docs/DEPLOYMENT.md`; every environment variable per platform: `docs/ENV-PRODUCTION.md`.

- **Website on Vercel** (Pro, functions in Frankfurt `fra1`): Root Directory `frontend`, settings in `frontend/vercel.json` (install with the exact pnpm version and the lockfile, filtered to the website and `shared/`; only `main` deploys, no previews). Domains: `rassmstore.live` (main), `www` redirects to it, `admin.rassmstore.live` = the dashboard (`ADMIN_HOST`).
- **API on Render** (Starter, Frankfurt): `render.yaml` Blueprint with two services, `rassm-api` (web, `/health`, `api.rassmstore.live`) and `rassm-backup` (cron, every night 02:00 UTC = 03:00 in Algeria: `pnpm backup` encrypted, copied to a Backblaze B2 bucket that deletes copies after 14 days). Both install only `@rassm/backend` and its workspace dependencies (`--prod`) and run TypeScript with `node --import tsx`. The daily client-data purge runs inside the API (no cron needed).
- Versions: Node.js 24 (`.node-version` for Render, `engines` `24.x` for Vercel), pnpm from `packageManager` (the same version is written in `vercel.json` and `render.yaml`: `backend/test/deployment.test.ts` checks they match; change all three together).
- The website refuses to build or start as an https site with a missing or weak `ADMIN_PROXY_SECRET`, `REVALIDATE_SECRET`, `TRUST_PROXY` or a non-https API (`src/lib/production-env.ts`, run by `next.config.ts`), like the API (`env.ts`). One-off commands use `loadEnv("task")`: the web server settings (`TRUST_PROXY`, `ADMIN_PROXY_SECRET`, `ADMIN_URL`) are not required there, every other check stays (the backup cron job only has the database, the passphrase and the bucket).
- `GET /health/ip` (API) shows the caller the IP the API sees and the `X-Forwarded-For` entries: the check of `TRUST_PROXY` once deployed (Vercel overwrites `X-Forwarded-For` with the visitor IP: `TRUST_PROXY=1` in the website).
- Off-site backups (`lib/offsite-storage.ts`): one S3 `PUT` signed with AWS Signature V4 (tested with the AWS examples), Backblaze B2 or Cloudflare R2, never an unencrypted file; a failed upload fails the cron run (Render e-mails).

## Security

How the site is protected, where every secret lives and how to rotate it, backups and restoring: `docs/SECURITY.md`.

- Before adding any new outside service or script (TikTok Pixel, Google Analytics, chat widget, new font or image host...), add its domains to `frontend/src/lib/security-headers.ts`, otherwise the browser will block it. Test the page for CSP errors after adding it.
- Never cancel a "Suspecte" order automatically; it may be a real customer, so call first.
- Many mobile customers in Algeria share one IP address (carrier-grade NAT): a rule per IP may flag or alert, but must never block normal customers.
- Keep `/confidentialite` true: any new data collected, new cookie, new provider or new event sent to Meta goes on that page (and in `docs/SECURITY.md`).

## Code rules

- TypeScript `strict` everywhere. **No `any`** (lint error). Prefer types inferred from Zod schemas.
- Small, reusable components. Shared UI goes in `frontend/src/components/`, not copy-pasted.
- **Data access only through `frontend/src/lib/data/`** (`getFeaturedProducts`, `getCategoryCards`, `subscribeToNewsletter`…). Components and pages never call `fetch` or import `@rassm/shared/mocks`: only `lib/data/` talks to the API.
- **Mobile first:** write base styles for 375px, then add `md:` / `lg:` overrides.
- Secrets and URLs go in env variables. Every app with env vars has a committed `.env.example`. Never commit `.env*` files. Where each secret lives and how to rotate it: `docs/SECURITY.md`.
- Use the `@/` alias for imports inside `frontend/src`.
- Prettier formats code (Tailwind classes are auto-sorted). ESLint runs with the shared config.

## Definition of Done (every task)

1. Run `pnpm typecheck`, `pnpm lint` and `pnpm test` from the root and fix all errors in every workspace.
2. Run the app (`pnpm dev`) and check there are **no terminal or browser console errors**.
3. For UI work: compare the result with `design/Homepage.png` at **375px, 768px and 1440px** widths. Headless Chrome cannot go below ~500px, so check 500px automatically and let the user check 375px.
4. End with a short summary: what was done, and what the user needs to do or decide.
